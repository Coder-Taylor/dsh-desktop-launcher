# DSH Launcher

面向 Windows 与 Linux 的非官方 DeepSeek Harness 图形化启动器。目标是让用户双击一个轻量 EXE，完成 DSH 的检测、安装、启动、更新与维护；所有耗时操作在后台执行，但会显示清晰的状态和本地日志。

项目目标：

- 一键安装、启动、停止和打开 DeepSeek Harness Web UI；
- 后台静默检查并安全更新 DSH；
- 后台检查并更新启动器自身；
- 保留用户的 `DSH_HOME` 配置、凭据和会话数据；
- 同一套 GUI 与核心逻辑同时支持 Windows 和 Linux；
- Gitee Releases 面向国内用户优先下载，GitHub Releases 作为备用源并支持双源故障切换。

当前根目录的 `启动DeepSeek Harness.bat` 是现有 Windows 原型，在新版 GUI 达到可替代状态前继续保留。

## 使用方式

### 已安装 DSH

- 双击启动器：启动 DSH，并在后台检查 DSH 与启动器更新；DSH 自身只请求打开一次网页，没有更新时启动器在 30 秒后关闭；
- DSH 已运行：可打开网页、停止服务或手动检查更新；
- “设置 → 通用”可开启“启动成功 30 秒后最小化到系统托盘”；托盘菜单可恢复窗口、打开网页、停止服务或退出；
- 点击右上角 × 时可选择退出、最小化到托盘或取消，并可勾选“记住我的选择”；“设置 → 通用”也能随时切换为每次询问、托盘或直接退出；这些操作都不会停止正在运行的 DSH 服务；
- 手动检查发现更新：进入更新页后可选一键更新、仅更新 DSH 或仅更新启动器；
- DSH 更新默认使用国内 npm 镜像，可切换 npm 官方源；更新始终写回检测到的原安装目录，但会先在同盘隔离目录安装和校验，成功后才替换程序文件。

### 未安装 DSH

启动器会先给出“检测到 DSH 未安装”的明确提示。用户可选择默认或自定义安装目录、国内镜像或官方源；缺少 Node.js 时会先提示安装 Node.js。它还会检查启动 shim、DSH 核心包和版本命令；发现安装被中断或资源缺失时，显示“安装不完整”和“修复 DSH”，并使用此前记录的原目录重建程序文件，不会新建第二份 DSH。安装完成会进行版本校验，随后启动 Web 服务并由 DSH 自身请求打开网页。

### 更新为什么可能需要数分钟

DSH 0.1.1 的依赖较多，npm 首次更新需要解析完整依赖树、下载软件包并执行安装脚本。旧版固定 1 GiB Node 堆上限，会在 `idealTree` 阶段内存不足，看起来像“下载卡住”。新版按可用内存动态设置受限的 Node 堆与子进程组内存上限，同时保留取消、超时和实时状态心跳。真实国内镜像更新已校验到 `0.1.1-rc.2`。

### DSH 更新的两级方案

启动器按以下顺序更新 DSH：

1. **常规更新（首选）**：选择官方 npm 源或可用国内镜像，在原安装目录旁的隔离目录执行 npm 更新；通过版本和启动 shim 校验后，才以目录改名完成切换。原版本在短时间内保留为回滚备份。
2. **修复重装（兜底）**：当常规更新失败、被取消、发现 shim/核心包/版本命令缺失，或上次安装留下不完整状态时，读取启动器记住的原安装目录、Node.js 路径、镜像偏好和 DSH_HOME，重新在隔离目录安装并校验，再安全替换到原目录。

旧 BAT 的“定位 Node.js、原安装目录、环境变量和启动参数”逻辑可以继续复用为兼容参考；但**不能**采用“先卸载再安装”作为自动兜底：一旦下载、解析或用户取消发生在两步之间，原本可用的 DSH 会被删掉。GUI 的修复重装应始终保留旧文件，只有新副本可启动且校验通过后才切换；切换失败则继续保留或恢复旧版本。用户明确选择“卸载 DSH”时才执行真实删除，且不删除 DSH_HOME、凭据和会话数据。

## 日志与隐私

日志默认存放在：

```text
%LOCALAPPDATA%\DshLauncher\logs\launcher.log
%LOCALAPPDATA%\DshLauncher\logs\dsh-web.log
```

日志会记录安装目录、版本、下载源、命令退出码、超时和校验结果；不会记录 API Key、凭据、会话正文或完整环境变量。日志会轮转，并自动清理过期文件。

## 测试版状态

`v0.1.1-beta.10` 是已发布到 Gitee、并同步 GitHub 的公开预发布版本。**只有启动器自身更新已完成实机验证。DSH 更新和首次安装当前均不能正常使用，不能视为已发布功能。**针对 DSH 0.1.1-rc.2 的 npm peer 依赖解析循环，代码已尝试使用 `--legacy-peer-deps` 并显式安装运行时 peer 包；更新也已采用“隔离安装、双重版本校验、带备份替换”。这些实现仍需修复并在 Win10/Win11 完成完整验收。服务状态必须连续两次通过 HTTP 健康检查才会显示为运行中。

## 后续开发计划

已验证的是**启动器自身更新**。DSH 更新和首次安装当前不可用，卸载尚未实测；下面是 DSH 管理能力下一轮的明确工作顺序。每项完成前不会标记为正式稳定版。

1. **资源完整性验证与修复**：启动、更新和“打开网页”前检查已记录原目录中的 Node.js、`dsh` 启动 shim、`@deepseek-ai/dsh/package.json` 与 `dsh --version`。任一关键资源缺失、版本命令失败或上次切换残留未完成时，必须显示“安装不完整/可修复”，禁止显示“DSH 正在运行”或打开浏览器；修复应在隔离目录重装、校验后再切换，并保留旧副本回滚。
2. **DSH 更新可用化**：先使已有 DSH 的常规更新在启动器内稳定完成；再在 Win10、Win11 覆盖国内镜像、官方源、取消、强制关闭、网络失败、修复重装及服务短暂退出。重点验证中断后重开启动器不会误报运行、不会破坏原可用 DSH。
3. **首次安装可用化**：完成下载/安装 DSH 与下载/安装 Node.js；在干净 Win10、Win11 环境验证默认目录、自定义目录、国内镜像和官方源。首次安装未达到可用前，不宣传“一键安装”。
4. **卸载流程**：完成卸载 DSH、卸载 Node.js 的隔离环境测试；卸载仅在用户明确确认后执行，并默认保留 `DSH_HOME`、凭据和会话数据。
5. **发布与诊断收尾**：完善更新失败日志和一键导出诊断信息；后续新 Release 安装包随附 `LICENSE`，并继续保留 Gitee 主源、GitHub 备用源和 SHA-256 校验。

实现顺序上，优先完成第 1、2 项，再实现首次安装并补齐卸载验收；这样即使用户中途中止操作，也不会出现“界面显示正常、实际 DSH 文件或服务已失效”的状态。

后续可加入“半自动配置 API Key”：启动器先打开官方网页并引导用户获取 Key；用户自行复制后，启动器在明确授权的短时间内监听剪贴板并自动填写。Key 不写入日志、不上传、不在启动器内长期保存，监听结束后立即停止。
