# DSH Desktop Launcher 开发指南

本文档是项目当前开发、验收和提交的执行规范。它用于防止界面修复、安装流程、DSH 更新和启动器自更新再次同时叠加。

如本文档与早期 `PROJECT_PLAN.md` 或 `ARCHITECTURE.md` 的实现顺序冲突，以本文档为准；产品安全边界仍以架构文档为准。
界面、安装与卸载的最终产品设计以 [`UI_DESIGN.md`](UI_DESIGN.md) 为准；旧页面的
现有代码不得被当作已验收的设计。

## 1. 当前状态

截至 2026-08-30：

- `v0.1.1-beta.10` 已作为 Gitee 主 Release、GitHub 备用 Release 公开预发布；更新清单已指向两端相同 SHA-256 的包；
- 启动器自身更新已经完成真实下载、校验、替换与重启验证；
- DSH 更新采用隔离安装、版本/启动 shim 双重校验、同卷切换和可恢复备份；修复重装保留原目录、Node.js 路径、镜像偏好和用户数据；
- DSH 的取消、中断、修复重装、成功更新与服务短暂退出仍需在 Win10/Win11 完成实机验收，不能因启动器自更新通过而标记为完成；
- 原 BAT 继续保留为兼容参考；可复用其路径和参数探测，但不得用“先卸载、后安装”破坏式流程替代隔离更新；
- 项目自有代码、脚本和文档使用 [MIT License](../LICENSE)；DSH 上游及其依赖、名称与商标不包含在此授权内。详见[授权说明](LICENSING.md)。

## 2. 产品目标

启动器必须保持“像 BAT 一样直接，但比 BAT 更清晰”的体验：

1. 双击后立即出现主界面；
2. 先做本地检测，不因网络阻塞窗口显示；
3. 缺少 Node.js 或 DSH 时提供一键安装；
4. 已安装 DSH 时读取并继续使用原安装目录；
5. 发现更新时在主界面说明版本、路径和更新源；
6. 用户确认更新后，更新完成并校验通过才启动 DSH；
7. 启动成功后自动打开 Web UI；
8. 启动器窗口可自动关闭，DSH 服务继续后台运行；
9. 所有命令和检查不闪出 CMD、PowerShell 或终端窗口；
10. 用户随时能看懂程序当前在做什么。

优先级固定为：正确性 > 数据安全 > 可理解性 > 启动速度 > 功能数量。

## 3. 不可破坏的行为约束

### 3.1 现有 DSH

- 从检测到的 `dsh.cmd` 或可执行文件反推出原安装目录；
- 不把已有 DSH 静默迁移到启动器托管目录；
- DSH 更新必须写回原安装目录；
- npm 不得直接写入原目录的活跃 `node_modules`、`package.json` 或锁文件；必须先在同一卷的隔离目录完成安装和版本校验，再带备份替换这三项程序文件；
- 发现 shim、`@deepseek-ai/dsh/package.json` 或 `dsh --version` 缺失/失败时，必须标记为“安装不完整”，并把一键安装改为在记录的原目录执行修复；
- 更新前显示当前版本、最新版本和原安装目录；
- 用户确认后才更新；
- 更新后重新读取原可执行文件并校验版本；
- 校验失败时不启动一个状态不明的新版本；
- 永不移动、删除或记录用户的 `DSH_HOME` 内容。

### 3.2 新安装 DSH

当电脑上不存在 DSH 时，用户可以选择：

- 默认目录：`%LOCALAPPDATA%\DshLauncher\runtime\dsh`；
- 自定义目录：通过系统文件夹选择器选择。

安装完成后记录实际 `dsh.cmd` 路径。后续启动和更新都使用该精确路径，不依赖 PATH 顺序。

### 3.3 Node.js

- 已有可用 Node.js/npm 时优先复用；
- 缺少时默认采用用户级安装，尽量不要求管理员权限；
- 默认国内镜像，用户可切换官方源；
- Node.js 安装目录与 DSH 安装目录分别记录；
- 需要支持默认目录与自定义目录两种安装方式；
- 不静默改写系统级 PATH；需要变更时必须明确告知用户。

### 3.4 BAT 功能对照与兼容要求

原 BAT 已具备的基础能力，启动器必须提供等价操作；界面可以更简洁，但不能无故丢失功能：

- 检测 DSH、Node.js/npm、PID 文件和 3080 端口；
- DSH 未运行时后台启动，等待健康状态后打开网页；
- 已运行时提供打开网页、停止服务和卸载入口，但启动器不得因检测到外部服务再次自动打开网页；
- DSH 支持默认安装目录与用户自定义目录；
- Node.js 支持官方源、国内镜像、默认目录和自定义目录；
- 安装失败时支持切换源、重试和手动安装提示；
- 卸载 DSH、卸载 Node.js、同时卸载两者，且默认保留配置、会话和日志；
- 停止服务前校验 PID 和端口，不能误杀其他程序；
- 清理 PID、临时下载文件和用户 PATH 中由启动器添加的目录；
- 原 BAT 的 5 秒/30 秒等待可以改为 GUI 健康轮询，但必须有超时和明确错误。

启动器可以保留“打开即检查并启动”的简洁流程，不必复制 BAT 的文字菜单；但上述操作必须能从主界面或详细操作入口访问。

### 3.5 卸载约束

- 卸载前必须确认并停止由启动器管理的 DSH 进程；
- 只删除启动器记录的 DSH 安装目录或 npm 包，不按模糊名称递归删除用户目录；
- 默认卸载 DSH，不删除用户配置、会话、`DSH_HOME` 和日志；用户在卸载确认中取消
  “保留对话记忆”后，仅清除 `DSH_HOME/sessions` 与 `DSH_HOME/storages`，不删除设置、凭据、profiles 或日志；
- Node.js 卸载必须单独确认，默认不删除其他程序可能使用的 Node.js；
- 只有明确选择“同时卸载 Node.js”时，才清理启动器托管的 Node.js 运行时；
- 卸载失败时保留日志和剩余路径，不能报告为成功。

### 3.6 启动器自身

- 发现新版时显示当前版本与最新版本；
- 用户确认后才下载；
- 下载后校验 SHA-256；
- 校验成功后退出主程序，由独立更新助手立即替换；
- 替换成功后自动重启新版，不留到下一次手动打开；
- 替换失败时恢复旧版并写入明确日志。

## 4. 更新源定义

原 BAT 实际使用的源如下：

- DSH 国内源：`https://registry.npmmirror.com`；
- DSH 官方源：`https://registry.npmjs.org`；
- Node.js 国内源：`https://npmmirror.com/mirrors/node/`；
- Node.js 官方源：`https://nodejs.org/`。

原 BAT 没有使用清华 npm 源。

启动器自身使用：

- 国内默认：Gitee Release；
- 官方备用或用户选择：GitHub Release。

界面提供两种模式：

- `国内镜像（默认）`：Node.js 使用 npmmirror 并允许回退官方源；DSH 在 npmmirror、腾讯云、华为云中测速后选择最快可用源，启动器使用 Gitee；
- `GitHub / 官方源`：Node.js 使用 nodejs.org，DSH 使用 npmjs，启动器使用 GitHub。

源选择应保存到启动器配置，下次启动继续使用；日志需记录实际使用的源，但不能记录凭据或完整环境变量。

## 5. 界面信息架构

主窗口保持一个主要动作，不做复杂仪表盘。

### 5.1 首页固定信息

- DSH 状态：未安装、已停止、启动中、运行中、更新中或失败；
- DSH 当前版本；
- 启动器当前版本；
- 当前主要动作；
- 最近执行记录；
- 当前更新源。

运行状态使用绿点，停止状态使用红点。颜色不能作为唯一提示，必须同时显示文字。

### 5.2 详细信息

“详细信息”入口展开后显示：

- DSH 当前版本与检测到的最新版本；
- DSH 实际安装目录；
- 启动器当前版本与检测到的最新版本；
- 启动器构建类型、CPU 架构和更新通道；
- Node.js 与 npm 版本；
- 当前更新源；
- 启动器日志路径和 DSH 服务日志路径；
- “打开日志目录”按钮。

### 5.3 确认操作

安装和更新确认嵌入主窗口，不使用突兀的系统 `MessageBox`。

确认状态复用主状态卡和底部圆角按钮，例如：

- `立即更新 / 暂不更新`；
- `默认安装 / 自定义目录`；
- `重试 / 查看日志`。

### 5.4 执行记录

执行记录使用不透明背景的标准列表控件或自绘列表，不再使用透明只读编辑框。

要求：

- 最多保留最近 100 条界面记录；
- 新记录自动滚到底部；
- 用户可手动向上查看；
- 每个逻辑步骤只追加一次；
- 不能因刷新、滚动或高 DPI 重绘出现叠字；
- 网络与 npm 的长操作显示已用时间；
- 超时后显示明确错误，不允许无限“正在处理”。

## 6. 状态机与并发规则

任何时刻只允许一个管理操作：

```text
Idle
  -> Detecting
  -> WaitingForConfirmation
  -> Installing | Updating | Starting | Stopping
  -> Verifying
  -> Ready | Stopped | Error
```

规则：

- 安装、更新、启动和停止不得并行；
- 忙碌状态禁用会产生冲突的按钮；
- 更新源可以在确认下载前切换，下载开始后锁定；
- 关闭窗口时必须取消或安全收尾后台任务；
- 后台线程不得引用已经销毁的窗口或服务对象；
- 不使用无法管理生命周期的裸 `detach()` 线程；
- UI 更新统一投递到 UI 线程。

## 7. 隐藏命令执行规范

Windows 外部命令统一通过一个受测试的执行器运行：

- `CreateProcessW`；
- `CREATE_NO_WINDOW`；
- stdout/stderr 写入匿名管道；
- 父进程只继承必要句柄；
- 子进程加入 Job Object；
- Job 使用 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`；
- 所有需要执行外部命令的路径都必须成功加入 Job；无法创建或配置 Job 时立即终止子进程，不允许无上限运行；
- 执行器默认给普通检测命令 512 MiB Job 内存上限，只有经过评估的安装/更新命令才能显式提高上限；
- Node.js 下载/安装不设置固定可用内存门槛；DSH 更新也不按整机空闲内存提前拒绝，而由 npm 的动态 V8/Job 限额和实际退出结果决定；
- 安装前先探测所选 registry 的轻量 `/latest` 元数据；源不可达时直接失败，不拉起 npm 解析依赖树；
- DSH npm 更新按可用内存动态设置 V8 堆（1.5–3 GiB）和 Job 内存上限（2–4 GiB），并保留网络并发上限、取消与实时心跳；针对 npm 11 在 0.1.1-rc.2 app-boot peer 图上的放置循环，使用 `--legacy-peer-deps` 并显式补齐运行时 peer 包；
- Node.js 压缩包解压任务也加入独立 Job，内存上限为 512 MiB；
- 等待主进程退出，而不是等待所有管道写端自然消失；
- 主进程退出后排空剩余管道数据；
- 安装命令必须有超时；
- 超时后终止该 Job 内的进程树；
- 安装/更新期间提供“取消下载”按钮；取消只终止当前 Job，不自动切换源、不继续覆盖安装目录；
- 输出限制长度并脱敏后写入日志。

建议超时：

- 本地检测：5–30 秒；
- 版本查询：30 秒；
- Node.js 下载/安装：15 分钟；
- DSH 安装/更新：单源最多 15 分钟；若依赖解析超时，不切换到另一源重复同一长任务；
- 启动健康检查：90 秒。

不得使用 `-EncodedCommand`。能用 WinHTTP、文件 API、进程 API 完成的工作不调用 PowerShell。

## 8. DSH 更新协议

说明：原 BAT 没有完整的在线更新协议；本节是启动器新增能力，不得在 Stage 2 尚未通过前伪装成已完成。

1. 读取当前精确可执行路径与版本；
2. 国内模式按 npmmirror、腾讯云、华为云顺序探测，并选择本机测速最快的可用源；官方模式只使用 npmjs，不偷偷切回镜像。无本地代理时优先使用 WinHTTP；检测到 Clash/Verge 等本机代理时，版本元数据允许使用 npm/Node 的 OpenSSL 网络栈回退，避免 WinHTTP/Schannel 与浏览器代理路径不一致；WinHTTP 自动代理失败时再尝试 Windows 默认代理；
3. 无新版时记录“已是最新版本”，继续启动；
4. 有新版时进入主界面确认状态；
5. 显示版本对比、原安装目录和下载源；
6. 用户确认后锁定源选择；
7. 如果旧服务由启动器管理，先安全停止；
8. 对同一卷的 `<原目录>\\.dsh-launcher-staging` 执行 `npm install --prefix <隔离目录> @deepseek-ai/dsh ...`；不得让 npm 直接接触正在使用的程序文件。更新时必须显式指定目标版本 `@deepseek-ai/dsh@<最新版本>`；
9. npm 自定义前缀的可执行文件通常位于 `<隔离目录>\\node_modules\\.bin\\dsh.cmd`。必须先执行 `dsh --version` 并确认版本；失败、取消或超时时原目录不变，隔离目录原子改名后交给无窗口维护进程清理；
10. 校验成功后，把原目录的 `node_modules`、`package.json`、`package-lock.json` 逐项移到 `.dsh-launcher-rollback`，再把隔离副本移入原位置；替换后的版本再次校验才删除备份。若进程在替换窗口异常退出，下次启动必须优先用该备份恢复旧程序文件；不得触碰 `DSH_HOME`、插件、会话或用户配置；
11. 不再使用 npm 11.9 已废弃的 `--allow-scripts` 参数；实测标准 peer 解析超过 11 分钟仍停在同一放置阶段且占用超过 2.4 GiB，因此对 0.1.1-rc.2 显式补齐运行时 peer 包并使用 `--legacy-peer-deps`；国内模式只选一次测速最快的可用镜像，超时后结束该 Job 而不是重复十五分钟任务；
12. 大型 staging、rollback 与卸载目录只在前台执行同盘原子改名；递归删除交给启动器自身的 `--cleanup-directory` 隐藏维护模式，并严格限定只能删除以 `.dsh-launcher-` 开头的非根目录。
13. 版本符合预期才重新启动；
14. 失败时显示摘要并提供重试、切换源和查看日志；日志必须记录每个源的 URL、HTTP/WinHTTP 错误码，不能只写“更新失败”。代理 TLS 错误（例如 12185：代理要求客户端证书但当前账户没有私钥）必须单独说明。日志主文件不可追加时，必须自动写入带进程号的会话日志，不能让用户看到过期日志。

首次实现必须在隔离复制目录中验证，不能直接拿用户唯一的 DSH 安装目录做破坏性测试。

## 9. 启动器自更新协议

更新清单必须提供：

- schema 版本；
- 启动器版本；
- 发布时间与通道；
- Gitee/GitHub 包地址；
- 文件大小；
- SHA-256；
- 最低可直接升级版本；
- Release Notes 地址。

当前实现已经覆盖清单查询、大小/SHA-256 校验、独立暂存目录和隐藏替换助手；正式 Release 清单未发布时按钮保持禁用，不会假装可以更新。

流程：

1. 查询所选源的清单；
2. 比较语义化版本；
3. 在主界面请求用户确认；
4. 下载到 `.partial`；
5. 校验长度和 SHA-256；
6. 解包到独立暂存目录；
7. 启动隐藏更新助手；
8. 主程序退出；
9. 更新助手等待旧 EXE 退出后替换并重启；
10. 新版启动后重新进行本地检测。

备份/回滚和正式 Release 健康标志仍属于阶段 4 的未完成验收项，不能在没有实测前宣称已完成。

正式清单中的 SHA-256 不允许为占位符或全零。远程 Release 未准备好时，界面只能显示“尚未配置更新源”，不能假装已经完成自更新检查。

## 10. 日志与隐私

Windows 日志：

```text
%LOCALAPPDATA%\DshLauncher\logs\launcher.log
%LOCALAPPDATA%\DshLauncher\logs\dsh-web.log
```

日志规范：

- 启动、检测、源选择、命令退出码、超时和校验结果必须记录；
- 记录安装目录和版本，但不记录 API Key、凭据内容、会话正文或完整环境变量；
- 单文件 512 KiB 轮转；
- 保留最近 3 份；
- 清理 30 天前的日志；
- 界面记录是易读摘要，文件日志是排错详情。

### 当前界面状态约定

- 启动器首次打开时，先自动检查 DSH 与启动器更新；检查完成后停留在首页，不自动启动 DSH；
- 首页不显示下载源与更新操作。DSH 未运行时显示“启动 DSH / 检查更新”；DSH 正在运行时显示“打开 DSH 网页 / 停止服务 / 检查更新”；
- “启动 DSH”只启动服务，绝不触发第二次更新检查；
- 手动检查发现更新时，先显示“进入更新页 / 稍后更新”的阻塞式选择弹窗；选择稍后更新后返回首页；
- 检查结果为“已是最新”或“检查失败”时使用五秒自动消失的非阻塞通知；
- 下载源只在更新页显示，支持“国内镜像（默认）/ 官方源”下拉选择；
- 更新页将“一键更新 / 仅更新 DSH / 仅更新启动器”收纳为默认“一键更新”的下拉操作；
- 设置页采用左侧分类、右侧内容布局；日志入口与卸载维护只在设置页显示，卸载仍必须二次确认。

## 14. Git 工作流

- `main` 只保存已通过当前阶段验收的代码；
- 未完成实验使用 `wip/*` 本地分支；
- 每个阶段单独提交；
- 不把多个未验收功能塞入同一个提交；
- 不推送 WIP 分支，除非明确需要备份或协作；
- 不推送远程和创建 Release，除非用户明确确认。

建议提交示例：

```text
fix(ui): replace activity log with stable scrollable list
feat(info): show DSH and launcher runtime details
feat(setup): restore BAT-compatible install and launch flow
feat(update): update DSH in its existing installation directory
feat(self-update): add verified launcher replacement and rollback
```

## 15. 安全软件与发布信誉

无数字签名的新 EXE 仍可能被 SmartScreen、360 或火绒提示。降低误报风险：

- 不使用 UPX；
- 不使用 `-EncodedCommand`；
- 尽量使用 WinHTTP 和原生 API；
- 隐藏命令必须有清晰日志和固定用途；
- 更新包必须有 SHA-256；
- Release 提供公开源码、哈希和变更说明；
- 条件允许时使用可信代码签名证书；
- 发布前在本地 Defender 和用户指定安全软件中扫描。

安全软件“零误报”无法保证，但不得为了绕过检测使用混淆、加壳或规避扫描技术。

## 16. 完成定义

一项功能只有同时满足以下条件才算完成：

- 行为符合本开发文档；
- 编译无错误；
- 相关自动测试通过；
- 实际 GUI 验收通过；
- 不闪出额外命令窗口；
- 失败路径有明确提示和日志；
- 未破坏现有 DSH、配置和会话；
- `git diff --check` 通过；
- 已创建单一目的的本地提交。

“代码已经写了”不等于“功能已经完成”。
