# DSH Desktop Launcher 开发指南

本文档是项目当前开发、验收和提交的执行规范。它用于防止界面修复、安装流程、DSH 更新和启动器自更新再次同时叠加。

如本文档与早期 `PROJECT_PLAN.md` 或 `ARCHITECTURE.md` 的实现顺序冲突，以本文档为准；产品安全边界仍以架构文档为准。

## 1. 当前状态

截至 2026-08-22：

- `main` 最后一个已提交基线：`38652b9 feat: add compact native DSH desktop launcher`；
- 原 BAT 已独立保存在提交 `34fd19e`；
- 当前工作区包含未完成的安装、更新和更新助手实验；
- 这些未提交实验尚未通过回归测试，不得作为 Release 发布；
- 下一步应先把实验保存到本地 WIP 分支，再从稳定基线按阶段重做。

当前实验中已发现的问题包括：

- Windows 只读编辑框使用透明背景时，滚动或重绘会产生叠字；
- 快速命令退出后若没有排空管道，可能误判 `where dsh` 没有输出；
- npm 后代进程继承管道句柄时，等待 EOF 会导致界面永久停留在“正在更新”；
- 更新、源切换、自定义目录和界面确认同时开发，使验收边界不清晰；
- 当前远程仓库还没有可用于正式自更新的 Release 和有效更新清单。

## 2. 产品目标

启动器必须保持“像 BAT 一样直接，但比 BAT 更清晰”的体验：

1. 双击后立即出现主界面；
2. 先做本地检测，不因网络阻塞窗口显示；
3. 缺少 Node.js 或 DSH 时提供一键安装；
4. 已安装 DSH 时读取并继续使用原安装目录；
5. 发现更新时在主界面说明版本、路径和更新源；
6. 用户确认更新后，更新完成并校验通过才启动 DSH；
7. 启动成功后自动打开 Web UI；
8. 启动器窗口可自动关闭，DSH 服务继续后台运行；
9. 所有命令和检查不闪出 CMD、PowerShell 或终端窗口；
10. 用户随时能看懂程序当前在做什么。

优先级固定为：正确性 > 数据安全 > 可理解性 > 启动速度 > 功能数量。

## 3. 不可破坏的行为约束

### 3.1 现有 DSH

- 从检测到的 `dsh.cmd` 或可执行文件反推出原安装目录；
- 不把已有 DSH 静默迁移到启动器托管目录；
- DSH 更新必须写回原安装目录；
- 更新前显示当前版本、最新版本和原安装目录；
- 用户确认后才更新；
- 更新后重新读取原可执行文件并校验版本；
- 校验失败时不启动一个状态不明的新版本；
- 永不移动、删除或记录用户的 `DSH_HOME` 内容。

### 3.2 新安装 DSH

当电脑上不存在 DSH 时，用户可以选择：

- 默认目录：`%LOCALAPPDATA%\DshLauncher\runtime\dsh`；
- 自定义目录：通过系统文件夹选择器选择。

安装完成后记录实际 `dsh.cmd` 路径。后续启动和更新都使用该精确路径，不依赖 PATH 顺序。

### 3.3 Node.js

- 已有可用 Node.js/npm 时优先复用；
- 缺少时默认采用用户级安装，尽量不要求管理员权限；
- 默认国内镜像，用户可切换官方源；
- Node.js 安装目录与 DSH 安装目录分别记录；
- 不静默改写系统级 PATH；需要变更时必须明确告知用户。

### 3.4 启动器自身

- 发现新版时显示当前版本与最新版本；
- 用户确认后才下载；
- 下载后校验 SHA-256；
- 校验成功后退出主程序，由独立更新助手立即替换；
- 替换成功后自动重启新版，不留到下一次手动打开；
- 替换失败时恢复旧版并写入明确日志。

## 4. 更新源定义

原 BAT 实际使用的源如下：

- DSH 国内源：`https://registry.npmmirror.com`；
- DSH 官方源：`https://registry.npmjs.org`；
- Node.js 国内源：`https://npmmirror.com/mirrors/node/`；
- Node.js 官方源：`https://nodejs.org/`。

原 BAT 没有使用清华 npm 源。

启动器自身使用：

- 国内默认：Gitee Release；
- 官方备用或用户选择：GitHub Release。

界面提供两种模式：

- `国内镜像（默认）`：Node.js/DSH 使用 npmmirror，启动器使用 Gitee；失败后允许自动回退官方源；
- `GitHub / 官方源`：Node.js 使用 nodejs.org，DSH 使用 npmjs，启动器使用 GitHub。

源选择应保存到启动器配置，下次启动继续使用；日志需记录实际使用的源，但不能记录凭据或完整环境变量。

## 5. 界面信息架构

主窗口保持一个主要动作，不做复杂仪表盘。

### 5.1 首页固定信息

- DSH 状态：未安装、已停止、启动中、运行中、更新中或失败；
- DSH 当前版本；
- 启动器当前版本；
- 当前主要动作；
- 最近执行记录；
- 当前更新源。

运行状态使用绿点，停止状态使用红点。颜色不能作为唯一提示，必须同时显示文字。

### 5.2 详细信息

“详细信息”入口展开后显示：

- DSH 当前版本与检测到的最新版本；
- DSH 实际安装目录；
- 启动器当前版本与检测到的最新版本；
- 启动器构建类型、CPU 架构和更新通道；
- Node.js 与 npm 版本；
- 当前更新源；
- 启动器日志路径和 DSH 服务日志路径；
- “打开日志目录”按钮。

### 5.3 确认操作

安装和更新确认嵌入主窗口，不使用突兀的系统 `MessageBox`。

确认状态复用主状态卡和底部圆角按钮，例如：

- `立即更新 / 暂不更新`；
- `默认安装 / 自定义目录`；
- `重试 / 查看日志`。

### 5.4 执行记录

执行记录使用不透明背景的标准列表控件或自绘列表，不再使用透明只读编辑框。

要求：

- 最多保留最近 100 条界面记录；
- 新记录自动滚到底部；
- 用户可手动向上查看；
- 每个逻辑步骤只追加一次；
- 不能因刷新、滚动或高 DPI 重绘出现叠字；
- 网络与 npm 的长操作显示已用时间；
- 超时后显示明确错误，不允许无限“正在处理”。

## 6. 状态机与并发规则

任何时刻只允许一个管理操作：

```text
Idle
  -> Detecting
  -> WaitingForConfirmation
  -> Installing | Updating | Starting | Stopping
  -> Verifying
  -> Ready | Stopped | Error
```

规则：

- 安装、更新、启动和停止不得并行；
- 忙碌状态禁用会产生冲突的按钮；
- 更新源可以在确认下载前切换，下载开始后锁定；
- 关闭窗口时必须取消或安全收尾后台任务；
- 后台线程不得引用已经销毁的窗口或服务对象；
- 不使用无法管理生命周期的裸 `detach()` 线程；
- UI 更新统一投递到 UI 线程。

## 7. 隐藏命令执行规范

Windows 外部命令统一通过一个受测试的执行器运行：

- `CreateProcessW`；
- `CREATE_NO_WINDOW`；
- stdout/stderr 写入匿名管道；
- 父进程只继承必要句柄；
- 子进程加入 Job Object；
- Job 使用 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`；
- 等待主进程退出，而不是等待所有管道写端自然消失；
- 主进程退出后排空剩余管道数据；
- 安装命令必须有超时；
- 超时后终止该 Job 内的进程树；
- 输出限制长度并脱敏后写入日志。

建议超时：

- 本地检测：5–30 秒；
- 版本查询：30 秒；
- Node.js 下载/安装：15 分钟；
- DSH 安装/更新：5 分钟；
- 启动健康检查：90 秒。

不得使用 `-EncodedCommand`。能用 WinHTTP、文件 API、进程 API 完成的工作不调用 PowerShell。

## 8. DSH 更新协议

1. 读取当前精确可执行路径与版本；
2. 按用户选择的源查询 npm 最新版本；
3. 无新版时记录“已是最新版本”，继续启动；
4. 有新版时进入主界面确认状态；
5. 显示版本对比、原安装目录和下载源；
6. 用户确认后锁定源选择；
7. 如果旧服务由启动器管理，先安全停止；
8. 对原安装目录执行 `npm install --prefix <原目录> @deepseek-ai/dsh ...`；
9. 国内源失败时，仅在国内模式下回退 npm 官方源；
10. 命令完成后再次运行原路径的 `dsh --version`；
11. 版本符合预期才重新启动；
12. 失败时显示摘要并提供重试、切换源和查看日志。

首次实现必须在隔离复制目录中验证，不能直接拿用户唯一的 DSH 安装目录做破坏性测试。

## 9. 启动器自更新协议

更新清单必须提供：

- schema 版本；
- 启动器版本；
- 发布时间与通道；
- Gitee/GitHub 包地址；
- 文件大小；
- SHA-256；
- 最低可直接升级版本；
- Release Notes 地址。

流程：

1. 查询所选源的清单；
2. 比较语义化版本；
3. 在主界面请求用户确认；
4. 下载到 `.partial`；
5. 校验长度和 SHA-256；
6. 解包到独立暂存目录；
7. 启动 `dsh-updater`；
8. 主程序退出；
9. updater 备份旧 EXE并原子替换；
10. 启动新版并等待健康标志；
11. 新版失败则回滚旧版。

正式清单中的 SHA-256 不允许为占位符或全零。远程 Release 未准备好时，界面只能显示“尚未配置更新源”，不能假装已经完成自更新检查。

## 10. 日志与隐私

Windows 日志：

```text
%LOCALAPPDATA%\DshLauncher\logs\launcher.log
%LOCALAPPDATA%\DshLauncher\logs\dsh-web.log
```

日志规范：

- 启动、检测、源选择、命令退出码、超时和校验结果必须记录；
- 记录安装目录和版本，但不记录 API Key、凭据内容、会话正文或完整环境变量；
- 单文件 512 KiB 轮转；
- 保留最近 3 份；
- 清理 30 天前的日志；
- 界面记录是易读摘要，文件日志是排错详情。

## 11. 开发阶段与门禁

不得跨阶段叠加。每阶段都必须完成“实现、测试、截图验收、独立提交”。

### 阶段 0：恢复可控基线

- 创建本地 `wip/update-spike-backup` 分支；
- 保存当前未完成实验；
- 切回 `main` 的 `38652b9`；
- 确认工作区干净、可编译、核心测试通过。

验收：未完成实验可恢复，`main` 不包含半成品更新代码。

### 阶段 1：界面与信息

- 更换可靠的执行记录控件；
- 修复高 DPI；
- 显示 DSH 与启动器当前版本；
- 增加详细信息入口；
- 不增加安装或更新逻辑。

验收：100%、125%、150%、200% 缩放均无叠字、裁切和拥挤；连续追加 100 条记录仍可滚动。

### 阶段 2：BAT 基本流

- 检测 Node.js/npm/DSH；
- 默认与自定义目录安装；
- 国内镜像与官方源切换；
- 启动、健康检查、打开网页、停止；
- 不包含任何更新功能。

验收：在隔离环境完成“全无、仅有 Node、已有自定义 DSH、服务已运行”四条流程。

### 阶段 3：DSH 原地更新

- 查询版本；
- 内嵌确认；
- 原目录更新；
- 超时、错误和日志；
- 更新完成后启动。

验收：先在复制的测试目录升级成功，再由用户确认是否测试真实安装目录；旧版本、配置和会话可恢复。

### 阶段 4：启动器自更新

- 双源清单；
- 下载、哈希、替换、重启和回滚；
- 使用本地测试服务器或文件源模拟，不依赖尚未发布的远程 Release。

验收：成功升级、断网、哈希错误、解包失败和新版启动失败均有确定结果。

### 阶段 5：完整回归与发布

- Windows 全流程回归；
- Linux 基础流程回归；
- 无闪窗检查；
- 日志和隐私检查；
- Defender/安全软件误报评估；
- 创建版本提交与 Release 草稿。

验收：所有门禁通过后才允许推送正式 Tag 和公开 Release。

## 12. 测试矩阵

至少覆盖：

- Windows 10/11 x64；
- 100%、125%、150%、200% DPI；

- Node/npm/DSH 均不存在；

## 14. Git 工作流

- `main` 只保存已通过当前阶段验收的代码；
- 未完成实验使用 `wip/*` 本地分支；
- 每个阶段单独提交；
- 不把多个未验收功能塞入同一个提交；
- 不推送 WIP 分支，除非明确需要备份或协作；
- 不推送远程和创建 Release，除非用户明确确认。

建议提交示例：

```text
fix(ui): replace activity log with stable scrollable list
feat(info): show DSH and launcher runtime details
feat(setup): restore BAT-compatible install and launch flow
feat(update): update DSH in its existing installation directory
feat(self-update): add verified launcher replacement and rollback
```

## 15. 安全软件与发布信誉

无数字签名的新 EXE 仍可能被 SmartScreen、360 或火绒提示。降低误报风险：

- 不使用 UPX；
- 不使用 `-EncodedCommand`；
- 尽量使用 WinHTTP 和原生 API；
- 隐藏命令必须有清晰日志和固定用途；
- 更新包必须有 SHA-256；
- Release 提供公开源码、哈希和变更说明；
- 条件允许时使用可信代码签名证书；
- 发布前在本地 Defender 和用户指定安全软件中扫描。

安全软件“零误报”无法保证，但不得为了绕过检测使用混淆、加壳或规避扫描技术。

## 16. 完成定义

一项功能只有同时满足以下条件才算完成：

- 行为符合本开发文档；
- 编译无错误；
- 相关自动测试通过；
- 实际 GUI 验收通过；
- 不闪出额外命令窗口；
- 失败路径有明确提示和日志；
- 未破坏现有 DSH、配置和会话；
- `git diff --check` 通过；
- 已创建单一目的的本地提交。

“代码已经写了”不等于“功能已经完成”。
