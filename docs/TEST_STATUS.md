## 当前环境实测

2026-08-26 的本机网络路径曾出现 WinHTTP 直连失败；该现象与浏览器/Clash 的代理路径不同，
不能据此判断 DSH 包或国内镜像不可用。

2026-08-27 的隔离更新等价测试补充了以下事实：

- 可用内存约 12 GiB 时，`registry.npmmirror.com` 能持续返回 DSH 0.1.1-rc.2 的大量依赖元数据；
- 测试复制了原安装的 `package.json/package-lock.json` 到独立目录，未触碰 `E:\Software\DeepSeek Harness`；
- npm 在依赖树解析约 40 秒后已使用约 560 MiB，测试在继续增长前被主动终止；
- 旧启动器日志中四次 npm 尝试都停在 `idealTree/placeDep`，没有 npm 正常结束行；旧实现固定
  `NODE_OPTIONS=1024 MiB` 和 `Job=2 GiB`，且对每个源重复“兼容参数/标准参数”两次；
- BAT 中的 `--allow-scripts=...` 已在当前 npm 11.9.0 被核验为“未知配置”；它不阻止 npm 默认执行安装脚本，
  启动器因此使用等效且无警告的标准 `npm install`。国内镜像失败后才切官方源；根据当前可用内存动态设置
  1.5–3 GiB V8 与 2–4 GiB Job 上限，并为每次尝试记录实际峰值。
- 2026-08-27 的最新版还会在 npm 正在执行时同步它的输出；若 npm 保持静默，日志每 15 秒追加一次
  “正在处理依赖或下载中”的心跳。新的线上验证只需保留这份日志，即可区分下载、依赖解析、超时、取消和内存限制。
- 同日的完整隔离命令以 `NODE_OPTIONS=1536 MiB` 运行了 331 秒；国内镜像持续返回依赖元数据，最终报出
  `JavaScript heap out of memory`，没有任何网络错误。由此确认旧版固定 1024 MiB 的 V8 上限必然不足。
  启动器在可用内存充足时会选择 3072 MiB V8 / 4096 MiB Job；总任务超时也从 5 分钟延长为 15 分钟，
  但保留用户取消、单次网络请求 45 秒限制、每 15 秒心跳和 Job 进程组内存硬上限。
- 随后对原安装目录 `E:\Software\DeepSeek Harness` 的真实更新已完成：其中
  `node_modules\@deepseek-ai\dsh\package.json`、项目 `package.json/package-lock.json` 的写入时间为
  2026-08-27 12:24，包版本及 `dsh.cmd --version` 均为 `0.1.1-rc.2`；同一时段的 npm 缓存日志最后两行是
  `verbose exit 0` 与 `info ok`。因此“更新完成后直接打开网页”在此次运行中表示更新已成功、随后按既定流程启动服务，
  并非下载失败。
- 启动器自更新首次真实测试发现旧 `.cmd` 替换助手把 UTF-8 中文路径按 Windows 本地代码页解释，导致
  ZIP 已验证但目标 EXE 未替换；改为带 UTF-8 BOM 的 PowerShell `LiteralPath` 脚本，并移除会令 PowerShell
  提前退出的 `DETACHED_PROCESS` 后，中文路径回归成功。测试前后哈希分别为驱动器构建哈希和已发布
  beta.1 EXE 哈希 `5acf4631b6cbc54e903c3fa2a39c0a0823a2863b352b8ae26ce52f07db3724bb`，且新版进程已重启。
- beta.2 发布并公开清单后再次运行同一中文路径回归：清单返回 `0.1.1-beta.2`，更新驱动器返回
  `replacement_scheduled=true`，替换后 EXE 哈希为
  `e107e4279fa26e9e596062da8016a99c66847a16c80ad4a59f0e298497b8bf68`，与 beta.2 ZIP 内发布 EXE
  完全一致；重启进程存在并已在测试结束后清理。

此前记录的网络现象如下，供代理/TUN 诊断使用：

- `netsh winhttp show proxy`：`Direct access (no proxy server)`；
- `HTTP_PROXY/HTTPS_PROXY` 环境变量未配置；
- npmmirror、腾讯云、华为云、npmjs 和百度的 TCP 443 测试均失败；
- DNS 对多个域名仍可解析；
- 失败日志为 `WinHTTP 12029`，即 HTTPS 连接无法建立。
- 本机存在 Clash Verge 的 `127.0.0.1:7897` 监听；通过该代理的 WinHTTP HTTPS 握手返回 12185，而 npm 使用 Node/OpenSSL 可正常查询 DSH 版本。
- 因此“浏览器可打开百度、启动器直连失败”是网络路径不同；当前不是 DSH 版本不存在。启动器已经对 DSH 元数据切换到 npm 代理回退，但 GitHub/Gitee 的启动器清单仍需 WinHTTP TLS 或可用 Release 清单才能验证。

这说明失败发生在本机 HTTPS 出口、系统代理、TUN 路由或防火墙层面，不是某一个 DSH 包版本不存在。若浏览器能联网而这里仍失败，需要检查浏览器代理是否只配置在浏览器/用户代理中，而没有同步到 WinHTTP 或 TUN 路由。

## 发布门槛

在以下条件满足前，不应把当前构建标记为 Release：

1. 至少一个国内源能完成 DSH 元数据检查和真实安装/更新；
2. 更新失败、取消、切源和重试均有可见日志；
3. 已运行服务、启动器启动服务两种情况下都只打开一个网页；
4. 安装、更新、卸载在隔离目录完成回归；
5. Windows 和 Linux 的已实现功能分别通过平台测试；
6. 当前工作区先提交到本地 Git，再推送到 Gitee/GitHub。
